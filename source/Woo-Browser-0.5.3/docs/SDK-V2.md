# SDK API v2 and protocol boundaries

Source entry: `sdk/index.cjs`, MIT license, Node built-ins only. API version 2 adds conservative clock pauses, `release-pending`, explicitly confirmed release, bounded checkpoint v2 and an uninitialized identity gate. Signed envelopes and static-content manifest schemas remain v1. Extension manifests remain v1. Clients must handle the new pending state; do not assume reaching a deadline releases a name.

Ownership calls: `challenge`, `apply`, `resolve`, `inspect`, `maintain`, `setAvailable`, `finalizeRelease`, `export`. `inspect` permits reading the last verified local record while paused; it does not authorize signing or establish current network availability. `finalizeRelease(name,{confirmed:true,expectedGeneration,expectedOwner})` is an operator-only local interface, not a public unauthenticated API. The reference app exposes no real-name release UI. Test fixtures explicitly invoke it for fictitious names.

Checkpoint calls: `saveCheckpoint(registry,path)`, `restoreCheckpoint(path,{clock})`, `validateCheckpoint`. Writes and reads share the same structural/size constraints. Write rejection leaves the previous file untouched. Old detailed events are compacted, with a count retained; ownership records and generation counters are never removed by compaction. Restores always pause. Default caps: 2,000 records/rate subjects, 512 recent events, 4 MiB file; configured attempt caps cannot exceed supported checkpoint bounds. This is trusted local persistence, not a signed remote database or transaction service.

Clock calls count elapsed time only while available and within `maxUnobservedMs` (default 120,000). Longer gaps are discarded entirely and require explicit resume. The app samples every 30 seconds and pauses on OS suspend. Tests use either stepped healthy observations or an explicitly large fake-clock tolerance to model known healthy intervals. No production automatic release exists, providing an additional safeguard against timing uncertainty.

Host/client calls: `buildBundle`, `bundleRoot`, `verifyBundle`, `startHost`, `readLocalHost`, `VerifiedSiteClient`. Content signatures use Ed25519 over canonical JSON with sorted object keys; roots/files use SHA-256. Registry metadata stores public identity, generations, sequences and content hashes, not website bytes. The local Host serves bounded signed bundles on loopback only. The reference app caches signed bundles separately, restores the selected folder, and republishes the already signed snapshot after restart without generating a key. It does not re-read changed folder contents or sign new content until a valid signing identity is available.

`src/native-renderer.cjs` is the shared production renderer factory. It verifies ownership/revision/content, assigns an origin containing the full owner-generation identity, stores browser data in an identity-checked short path, installs deny-by-default permissions and request guards, and revokes previous-generation windows/protocol serving. Tests invoke this same factory after actual signed lifecycle transitions. Native cookies are unsupported in the tested runtime; IndexedDB and localStorage are tested.

`UninitializedIdentity` reports `configured:false` and rejects signing. It deliberately has no generation, activation, encryption or persistence method. Ephemeral test/demo signing occurs only through explicit fixture creation in the temporary lab. Real keys require a separately approved implementation/activation step.

Transport planning still returns labeled unimplemented direct/relay scenarios. No remote registry trust or public write endpoint is added. The local operator still controls database/admission and can tamper with their own service. Owner signatures protect the normal mutation interface, not against a malicious authoritative operator. Full-source client forks do not confer another owner's signing key.
